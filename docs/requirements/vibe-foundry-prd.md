# VibeFoundry 需求文档

## 1. 项目概述

**项目名称：VibeFoundry**

**长期愿景（2026-09-08 用户明确）：** 炼化一切，将所有信息资产转变为可供 AI 和人使用的“装甲”。可追溯、可检索、可复用是资产基础；最终还要帮助使用者执行任务、运用方法、完成创作。当前工程、书籍和文化材料是已接入的起点，具体装甲形式与效果验收需要后续计划定义。

**前端组件当前优先要求：** 尽量保留原组件视觉与交互依据，重复炼化复用未变源码的分析结果。提示词帮助产品人员把“看到了想要的组件效果，但不会专业描述”转化为设计需求，默认按布局、视觉、动效、交互详细分项，交给其他 AI 使用；不复制源码包。验收区分源码依据、实际挂载和实机视觉比较，不把三者视为同一质量等级。当前实施入口为[组件效果提示词计划](../plans/2026-09-08-component-effect-prompts.md)。

VibeFoundry 是一个面向 AI 创作和 AI 编程时代的“资产炼化器”。它从已经完成或半完成的 vibe 项目、业务流程、产品方案、文档资料、书籍和文化材料中提取可复用固定资产，包括前端组件、后端接口、业务模块、产品设计模式、设计 tokens、交互规范、代码约定、测试样例、文化隐喻、命名体系和 agent 使用规则，并把这些资产整理成可被人类和 AI agent 共同使用的资产包。

项目的核心判断是：AI 生成代码、页面、文案和方案会越来越便宜，但跨项目沉淀、复用、组合和治理仍然稀缺。VibeFoundry 不直接竞争“从 0 生成应用”的 AI app builder，而是服务于“从已有材料反向沉淀资产，再反哺新项目、新产品和新创作”的流程。

## 2. 背景与问题

**书籍当前目标（2026-09-08）：** 世界观、人物角色卡、设定、概念与隐喻网络，要求借鉴开源设计后自行开发。由同一套带来源的结构生成给人阅读和 AI 使用的资产，原文明确表达与解读分开。实施和未完成范围见[书籍知识资产计划](../plans/2026-09-08-book-knowledge-assets.md)。

AI 编程工具让个人和小团队能快速生成页面、组件和业务逻辑，但实际使用中会产生几个稳定问题：

- 每个项目都会重复生成类似组件、接口和业务流程，复用率低。
- 同一团队的多个 vibe 项目视觉风格和代码习惯容易漂移。
- 可复用资产散落在源码中，缺少结构化索引。
- AI agent 很难判断哪些组件、接口、业务流程或产品设计思路是通用资产，哪些只是临时代码。
- 登录/注册、权限、计费、邀请、审核等后端业务能力经常被重复实现，但很少被抽象成可复用业务资产。
- 设计语言、命名习惯、错误处理、空状态、loading 状态等隐性规范很难被下一次项目自动继承。
- 产品设计中的隐喻、世界观、仪式感、叙事结构、命名系统往往来自书籍、文化和文明材料，但这些思考通常只停留在人的笔记里，无法被 agent 稳定复用。

VibeFoundry 解决的不是“生成更多内容”，而是“把已经生成、已经验证或已经被人类文化长期沉淀的高价值部分变成可复利资产”。

## 3. 目标用户

### 3.1 首批用户

- 使用 Codex、Cursor、Claude Code、v0、Lovable、Bolt 等工具做项目的独立开发者。
- 高频交付 Web 应用、后台、落地页、SaaS 原型的 AI 编程工作室。
- 有多个相似项目、但还没有正式设计系统的小团队。
- 希望复用登录、注册、权限、支付、邀请等通用业务模块的全栈开发者。
- 希望把书籍、文化、品牌故事和产品思考转化为设计参考的产品经理、设计师和创作者。

### 3.2 后续用户

- 前端平台团队。
- 后端平台团队。
- 设计工程团队。
- 维护内部组件库和设计系统的中大型研发组织。
- 品牌、内容、游戏、教育、社区等重视隐喻和世界观设计的团队。

## 4. 核心价值主张

VibeFoundry 帮用户把一次性 vibe 产出转化为可持续复用的生产资料。

具体价值：

- **资产沉淀**：从真实项目和高价值资料中提取组件、接口、业务流程、tokens、页面模式、产品模式和隐喻系统。
- **复用提速**：新项目可直接引用既有工程资产和产品资产，减少重复生成。
- **风格一致**：降低 AI 生成 UI 的视觉和实现漂移。
- **业务一致**：降低登录、注册、权限、计费等通用能力在不同项目里的实现漂移。
- **创意复用**：把书籍、文明、神话、哲学和品牌材料中的隐喻设计炼化成产品创意资产。
- **agent 友好**：输出 MCP、Skill、规则文档等 AI 可读上下文。
- **渐进采用**：不要求团队先建立完整设计系统，可从一个真实项目开始。

## 5. 产品定位

一句话定位：

> VibeFoundry 从已有 vibe 项目中提炼可复用设计与代码资产，并生成可被 AI agent 调用的资产包。

扩展定位：

> VibeFoundry 从代码、业务流程、产品方案和文化材料中炼化可复用资产，让 AI 在后续开发、产品设计和创意构思中调用。

不是：

- 不是另一个 UI 生成器。
- 不是纯组件库。
- 不是单纯的 Storybook 插件。
- 不是只服务某一个 IDE 的提示词模板。
- 不是单纯的读书笔记工具。
- 不是通用知识库或 RAG 笔记系统；RAG 是 retrieval augmented generation，中文可理解为“检索增强生成”。VibeFoundry 的重点不是检索原文，而是提炼可复用资产。

是：

- 项目、业务和知识材料的反向资产蒸馏工具。
- AI-native asset distiller，中文可理解为“AI 原生资产炼化器”。
- 面向 agent 的资产索引、验证和复用层。

### 5.1 双核心路线

VibeFoundry 采用“双核心”路线：

1. **工程资产核心**
   - 先炼化前端组件、后端接口、业务模块、测试模板和工程规范。
   - 这是 MVP 的实现重点。

2. **创意资产核心**
   - 后续炼化产品设计思路、书籍隐喻、文化符号、世界观结构、命名体系和叙事模式。
   - MVP 阶段先在数据模型和输出协议中预留位置，不一开始实现完整书籍解析。

## 6. MVP 范围

本节保留最初 MVP 的范围定义。后续已实现本地 Web、规则式产品/隐喻提取、PDF/TXT/Markdown 书籍入口和预览动作缓存；这些增量的限制与未完成功能见 [2026-09-08 现状审计](../reports/2026-09-08-project-capability-audit.md)。后文“第一版不支持”不是对当前代码的描述。

### 6.1 输入

2026-09-15 Web 增量：用户可在网页内选择本机项目文件夹或 PDF/TXT/Markdown 文档，显式启动已有炼化链路，查看状态和真实结果。工程结果进入资产浏览；文档交付基础分析报告和 JSON，语义知识分析仍由宿主 AI 执行。详见[Web 本地选择与炼化](../plans/2026-09-15-web-local-import.md)。

第一版只支持本地工程项目目录，优先支持：

- React / Next.js
- TypeScript
- Tailwind CSS
- shadcn/ui 或类似组件结构
- Node.js / Next.js API routes / Express-like 后端代码的轻量识别
- 登录、注册、认证、权限等常见业务流程的启发式识别

第一版不直接支持整本书自动炼化，但输出协议会预留 `concept-assets` 和 `metaphor-packs`，方便后续接入书籍、笔记和文化材料。

### 6.2 输出

VibeFoundry 在集中资产库中生成项目资产包，不在源项目内创建 `.vibe-foundry/`。调用方显式传入的 `assetLibraryRoot` 优先，其次读取 `VIBE_FOUNDRY_LIBRARY_ROOT`，未设置时使用当前用户主目录下的 `.vibe-foundry/library`。项目资产目录包含：

- `asset-manifest.json`：资产总清单。
- `tokens.json`：颜色、字号、间距、圆角、阴影等设计 tokens。
- `component-catalog.json`：组件索引、用途、props、依赖、复用评分。
- `service-catalog.json`：后端接口、业务服务、认证/权限/计费等业务能力索引。
- `page-patterns.md`：页面模式总结，如登录页、Dashboard、表格页、详情页。
- `business-patterns.md`：业务流程总结，如登录/注册、邮箱验证、权限校验、订阅计费。
- `concept-assets.json`：产品设计资产、命名线索、隐喻主题和创意参考的预留结构。
- `agent-rules.md`：给 Codex/Cursor/Claude Code 使用的规则。
- `reuse-report.md`：复用价值、耦合风险、建议抽取顺序。

### 6.3 核心能力

1. **项目扫描**
   - 识别框架、包管理器、源码目录、组件目录、API 目录、服务目录、样式系统。
   - 读取 `package.json`、`tsconfig.json`、Tailwind 配置和源码结构。

2. **资产识别**
   - 区分通用组件、业务组件、页面组件、后端接口、业务服务和工具函数。
   - 根据引用次数、命名、依赖、props 泛化程度评估复用潜力。

3. **业务能力识别**
   - 识别登录、注册、认证、权限、会话、支付、订阅、邀请、通知、文件上传等候选业务资产。
   - 输出接口契约、输入输出、依赖、风险、安全约束和复用建议。

4. **设计语言提取**
   - 从 CSS、Tailwind class、主题配置和组件样式中提取 tokens。
   - 输出结构化 tokens，并标记来源。

5. **产品与模式总结**
   - 总结常见页面结构、布局模式、状态处理模式。
   - 总结常见产品流程，如 onboarding、注册转化、邀请、会员升级、内容发布。
   - 生成人类可读文档和 agent 可读规则。

6. **文化隐喻资产预留**
   - 预留从书籍、笔记和文化材料中提取隐喻、原型、符号、命名体系、情绪基调和世界观结构的资产模型。
   - MVP 不实现完整自动解析，但 schema 必须允许未来扩展。

7. **复用报告**
   - 给每个候选资产打分。
   - 标记高耦合、高风险、命名不清、缺少测试等问题。

## 7. 非 MVP 范围

第一版暂不做：

- 在线 SaaS 后台。
- 多人协作权限。
- Figma 双向同步。
- 自动重构源码。
- 自动发布 npm 包。
- 复杂跨语言后端资产识别。
- 完整书籍解析、版权文本存储和长文本知识库。
- 自动生成完整品牌世界观。
- 视觉截图比对和像素级设计 QA。

这些可以作为后续阶段扩展。

## 8. 用户流程

### 8.1 首次炼化

1. 用户进入已有项目根目录。
2. 运行 `vibe-foundry distill .`。
3. 工具扫描项目并在集中资产库中生成资产包。
4. 用户阅读 `reuse-report.md`，确认哪些资产值得沉淀。
5. 用户把 `agent-rules.md` 加入 `AGENTS.md`、Codex Skill 或 IDE 规则中。

### 8.2 新项目复用

1. 用户在新项目中连接集中资产库中的已有资产包。
2. AI agent 通过规则文档或 MCP 查询资产。
3. 生成新页面、新接口或新业务流程时优先复用既有组件、tokens、服务能力和业务模式。
4. 做产品设计时，agent 可查询已沉淀的产品模式、命名线索和隐喻资产。
5. 工具可运行校验，检查是否偏离资产规范。

## 9. 产品形态

VibeFoundry 不应该只做成 MCP 或只做成 Skill，而应分层设计：

- **CLI**：核心引擎，负责扫描、分析、生成资产包。
- **Skill**：Codex 工作流入口，告诉 agent 如何运行炼化流程、如何解释结果。
- **MCP Server**：资产查询和校验接口，供 agent 在新项目中按需调用。
- **Plugin**：面向 Codex 分发的打包形态，包含 Skill、MCP 配置和 CLI 辅助脚本。
- **Web Dashboard**：后期团队版，用于资产审查、版本管理和协作。

MVP 应先做 CLI，再补 Skill，随后做 MCP。

当前 CLI、Web、MCP 和书籍炼化共享同一集中资产库解析规则。Web 与 MCP 接收的 `projectRoot` 始终表示源码工程根，并由此定位集中资产包；当前消费者不再读取源项目 `.vibe-foundry/`，也不提供旧目录兜底。

## 10. 关键指标

### 10.1 产品指标

- 单个项目扫描成功率。
- 组件识别准确率。
- 后端接口和业务能力识别准确率。
- tokens 提取完整度。
- 资产报告可读性评分。
- agent 在新项目中复用资产的比例。
- 产品设计资产和隐喻资产在方案生成中的引用率。

### 10.2 用户价值指标

- 第二个类似项目的交付时间是否下降。
- UI 风格漂移是否减少。
- 通用后端业务流程重复实现是否减少。
- 重复组件数量是否减少。
- 人工整理组件库的时间是否减少。
- 从书籍/文化材料到产品设计参考的整理时间是否减少。

## 11. 主要风险

- **资产误判**：把业务组件、业务接口或一次性产品思路误认为通用资产。
- **抽象过早**：生成过多无价值资产，增加维护负担。
- **上下文丢失**：只提取代码，不保留用途和使用约束。
- **隐喻滥用**：从文化材料中提取的隐喻如果脱离语境，可能让产品设计变得生硬或误读原始文化。
- **版权风险**：书籍和长文本材料不能被当作可复制内容库，必须只保存摘要、结构化洞察和用户拥有权利的材料引用。
- **生态挤压**：Builder.io、Storybook、Bit、Figma 等工具可能向同一方向扩展。
- **技术栈过宽**：一开始支持太多框架会导致识别质量下降。

## 12. 成功标准

MVP 成功的最低标准：

- 能在一个真实 React / Next.js / Node.js 全栈项目对应的集中资产目录中生成完整资产包，且不在源项目内创建或读取 `.vibe-foundry/`。
- 报告能清楚列出 10 个以上可复用资产候选，至少覆盖前端组件和后端/业务流程中的一种。
- tokens 输出能覆盖主色、语义色、字号、间距、圆角。
- `agent-rules.md` 能直接被 Codex 用于新项目开发。
- 新项目开发时，agent 能按资产包复用至少 3 个组件、接口、业务模式或页面模式。
- 输出协议中包含产品设计资产和文化隐喻资产的预留字段，后续无需推翻 schema。
