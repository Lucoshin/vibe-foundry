# 项目现状与未完成功能审计

本文表格记录首次审计时点。随后已完成组件还原提示词、源码索引缓存和 Web/MCP 消费入口，MCP 工具数由 8 增至 9；当前交付与验证见[组件还原与提速验收](2026-09-08-component-reconstruction-validation.md)。通用装甲装配和实机视觉校准仍是缺口。

## 结论

后续书籍增量已交付宿主 AI 分块阅读、严格分析导入、世界观/角色卡/设定/概念/隐喻及离线关系图，见[首版验收](2026-09-08-book-knowledge-validation.md)。本文下方表格仍是首次审计的历史状态；自动模型执行、增量语义重炼及统一 Web/MCP 书籍消费尚未完成。

VibeFoundry 已有可运行的本地资产炼化底座，工程组件链路最成熟，CLI、集中资产库、Web、MCP、Skill 和 Plugin 也已连接起来。但“所有信息资产转成 AI/人可使用的装甲”尚未完成：目前大量输出是目录、规则分类、统计和固定建议，尚缺少从任务出发的能力交付、装配和效果验证。

“装甲”是用户本次明确的长期目标。本文将“使用者能借助产物完成什么任务”作为审计角度，不擅自把装甲限定为某一种文件格式或某个模型接口。

## 已有基础与质量评价

- **工程分析有实质实现。** `src/analyzers/frontend-source-index.ts` 已使用 React/Vue 语法分析，组件可保留真实调用场景、来源、未解析项和运行要求；这比仅按文件名生成清单更有复用基础。
- **集中库和执行边界清楚。** 源项目与生成产物分离，普通 `distill` 不执行源项目脚本，适合本地多项目沉淀。
- **预览缓存已实现。** SQLite 动作状态、内容寻址产物、租约、失败分类和挂载证据都已有实现与测试；不应列为未完成。
- **文档与测试投入较充分，但缺少跨项目和陌生材料回归。** 本轮基线 205 项测试中 204 通过，唯一失败为发布状态旧断言；新发现的身份冲突和默认虚构并未被原有用例覆盖。测试通过不能代替真实任务的复用验收。
- **后续维护压力集中在少数文件。** Web 前端把页面、样式和交互放在 `src/web/frontend.ts`，预览分析/生成/构建集中在 `src/preview/component-preview-runtime.ts`。应随明确功能边界逐步拆分，不为本轮审计先重构。
- **构建不是类型检查。** `scripts/build.mjs` 当前仅复制 `.ts` 文件为 `.js`；`tsconfig.json` 的 strict 设置不会由 `npm run build` 执行。现有验证依靠 Node 测试和运行行为。

## 本轮修复范围

对应 [实施计划](../plans/2026-09-08-asset-integrity-and-capability-audit.md)，本轮已修复以下可复现的已有契约问题：

- 中文文化材料独立文件相互覆盖、同批归一化名称冲突，以及重新生成遗留的旧 JSON。
- 未匹配材料被填入 `lens`、`guide`、`contextual` 等缺少证据的默认结果。
- 跨项目同名组件的标签、隐藏状态、预览身份串用，以及同项目异路径同名组件错误关联。
- Markdown 章节漏识别，以及过早截断来源造成后续章节关系丢失。
- 发布清单状态已更新而测试仍锁定历史阶段，以及总计划的陈旧当前限制。

这些修复提高资产真实性和来源隔离，不代表已实现通用语义提炼、自动装配或实机校准。

旧浏览器标签和隐藏记录不能准确映射到新身份，需要重新设置；旧包的重复预览 ID 会明确报错并提示重炼。英文隐喻文件名、现有词典和有效缓存协议保留，避免扩大本轮范围。已清理的废弃逻辑和产物边界详见实施计划完成记录。

## 明确暂缓的范围

原 MVP 明确未包含 SaaS、多人权限、Figma 双向同步、自动源码重构、npm 自动发布、复杂跨语言后端、外部大模型和向量检索。它们属于后续产品选择，不等同于本轮发现的实现缺陷。

源项目实机校准也明确不包含登录后页面、业务写操作、自动修复和远程采集。

开源清单在用户已有修改中声明首次公开已完成；本轮保留该文件，未重新核验远端设置，也未发布或推送。

## 下一阶段建议

优先交付一套能够验收的装甲，再扩展输入数量。以下是建议，尚未实现：

| 切入 | 最小交付 | 验收 |
| --- | --- | --- |
| 工程复用能力包 | 一个公开组件、所需样式/依赖、使用步骤和适用限制 | 装入第二个干净示例项目，构建和交互验证通过 |
| 书籍或资料方法卡 | 一篇自有方法说明的步骤、适用条件、限制和来源证据，并接入 Web/MCP | 人或 AI 按卡片完成一个指定任务，能解释采用了哪些来源方法 |
| 统一输入入口 | 工程与 Markdown 的类型识别、状态和统一发现入口 | 两种来源都能生成可查询资产，未知格式明确拒绝 |

建议先从工程复用能力包切入，因为现有工程分析和预览基础更强；如果用户优先希望增强分析决策，则先做资料方法卡。通用输入入口应服务已经验证的输出与任务，避免输入越来越多但产物依旧停留在目录。
